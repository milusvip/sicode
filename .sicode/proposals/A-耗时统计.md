## 结论（先看这个）

我直接用现有数据库跑了一遍（只读，未改任何代码），**推翻了我之前「瓶颈在轮次」的判断**：

| 指标 | 实测值 |
| --- | --- |
| 含工具调用的 assistant 消息 | 2595 条 |
| 总墙钟 | 53859s（约 15 小时） |
| **其中模型** | **35897s（66.6%）** |
| 其中工具 | 18032s（33.5%） |
| 平均每条消息 | 墙钟 20.8s　模型 13.8s　工具 6.9s |

**三分之二的时间花在模型出字上。** 工具只占三分之一。

再看工具内部（总 304 分钟）：

| 工具 | 次数 | 总耗时 | 占比 | 最长 |
| --- | --- | --- | --- | --- |
| **shell** | 1492 | **263.6min** | **86.6%** | 300.9s |
| question | 9 | 28.7min | 9.4% | 1147s |
| write | 314 | 3.7min | 1.2% | 74.8s |
| websearch | 55 | 3.6min | 1.2% | 55.2s |
| grep | 91 | 0.4min | 0.1% | 1.7s |
| **edit** | **385** | **0.2min** | **0.1%** | **0.3s** |

**edit 总共只花了 12 秒。** 385 次编辑，中位数 22ms，最慢 0.3s。

## 这对三个方案意味着什么

### 对方案 C（批量编辑）：期望值被高估了

`edit` 假设从 20ms 变成 0ms（无限并行），也只能省下这 12 秒——**占总墙钟的 0.02%**。

真正值钱的是**减少轮次**，不是把已有的编辑并行起来。每省一轮 = 省下那一轮的模型时间（平均 13.8s）。所以：

- **C1（提示词）的收益不在「并行」，在「一轮改完多个地方 = 少几轮」**。目标要改成「减少 round trip 数」，不是「提高并行度」。
- 实测并行度：一条消息 1 个工具 2281 次、2 个 283 次、3 个 23 次。**87% 是单工具**。

### 对方案 B（诊断回灌）：价值被低估了，但理由要换

诊断回灌原本的卖点是「省掉一轮自检」。现在看：

- 它救的不是 edit 的 20ms，而是**每一轮模型时间 13.8s**。一次「改错 → 下一轮才发现」的循环就是 13.8s × N。
- 按 226 次失败调用（见下）估算，若诊断能当场拦掉一半，省的是**几十轮的模型时间**，量级在分钟级。

**所以 B 的性价比高于 C。** 但前提是它真的能减少轮次——这需要 A2 后续验证（对比开关诊断前后的 `steps/turn`）。

### 对 A 本身：A1 已完成，A2 要改设计

原计划 A2 加「模型/工具/等待」三段分解。**实测发现这三段直接从现有字段就能算**（无需新埋点）：

- `modelMs` = 消息 `time_updated - time_created` − 工具耗时
- `toolMs` = Σ(`completed - ran`)
- 差值即等待

而 `stats.ts` 已经在算 `durationP50` 了。**所以要补的不是「算」,是「汇总到 turn 粒度 + 暴露」**。

## 关键修正：shell 才是工具侧的瓶颈（且多半是模型自找的）

437 个 shell 调用超过 5s，共耗 241 分钟（占工具总耗时 79%）。看最慢的几条：

```
[300.9s] node tools\attach-check.js 9333 ryJzPhQL
[300.9s] cd 'C:\Users\svip1\Documents\脚本'
[300.5s] node tools\diag-ds-edge.js 3.173.21.63
[282.6s] cd "...\ds-free-api"; echo "=== 已知成功端口存活检查 ==="; foreach ($p in 7000...
[270.8s] node tools\diag-lajiao-final.js
[260.4s] Get-NetTCPConnection -State Listen -LocalPort 1081
```

特征是**网络探测类脚本**：连不通就一直等到超时（300s 恰好是某个默认上限）。这不是 SiCode 慢，是**模型在跑注定超时的探测**。

由此得到一条独立于 A/B/C 的优化：**给 shell 探测类命令一个更激进的默认超时**，或在输出里提示「这类命令别串行试 5 个端口」。
- 现状：`shell.ts:29` 有 `DEFAULT_BACKGROUND_TIMEOUT_MS`（24h）和 `DEFAULT_TIMEOUT_MS`。
- 300s 出现在多条命令上，说明是某个统一上限被撞满。
