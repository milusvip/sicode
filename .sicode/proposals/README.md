# SiCode 提速方案总览

> 2026-10-28　｜　三份方案 + 实测数据　｜　全部待你拍板

## 一句话

**实测推翻了最初的假设**：时间的三分之二花在模型出字，工具只占三分之一；而工具的三分之一里，87% 又是 shell（多半是超时等待）。`edit` 总共只花了 12 秒——**「并行编辑」的收益天花板是总耗时的 0.02%**。

## 实测基线（2595 条含工具的消息，53859s 墙钟）

| 项 | 值 |
| --- | --- |
| 模型时间 | 35897s（**66.6%**） |
| 工具时间 | 18032s（33.5%） |
| 平均每轮 | 20.8s（模型 13.8s + 工具 6.9s） |
| 并行度 | **87% 的单条消息只发 1 个工具** |

工具内部 Top3：

| 工具 | 次数 | 总耗时 | 占比 |
| --- | --- | --- | --- |
| shell | 1492 | 263.6min | **86.6%** |
| question | 9 | 28.7min | 9.4% |
| write | 314 | 3.7min | 1.2% |
| edit | 385 | **0.2min** | **0.1%** |

shell 里 437 个调用 >5s，共 241 分钟。最长几条都是**网络探测脚本跑满超时**（300s）——不是 SiCode 慢，是模型在跑注定超时的命令。

## 四个方向与优先级

### ① 方案 B：语法回灌　→　**已实现** ✅
- 省的是 **13.8s/轮**的模型时间（改错当场发现，不用等下一轮）
- 消费端 UI 已就绪（`tool-renderer.tsx:147/183`）
- **原「只查 TS」方案已被实测推翻**：687 次编辑里 `.ts`/`.tsx` = **0 次**，tsgo 方案命中率 0%
- 改为按扩展名分发：JS/TS 族用 `bun build --no-bundle`、`.py` 用 `ast.parse`、`.sh` 用 `bash -n`、`.ps1` 用已有 tree-sitter 语法（进程内）、`.json` 用 `JSON.parse`
- `.cpp`（占 28%）**明确不覆盖**：本机无任何 C++ 编译器，不假装覆盖
- 落地：`packages/core/src/plugin/syntax-check.ts` + `packages/core/src/syntax-check/`，注册在 `plugin/internal.ts`
- 详见 `B-诊断回灌.md`

### ② shell 超时治理　→　**建议优先，且不依赖其他方案**
- 池子 241 分钟，是四个方向里最大的一块
- 做法：给探测类命令更激进的默认超时；或在结果里提示「别串行试 5 个端口」
- 现状 `shell.ts:29` 有 `DEFAULT_TIMEOUT_MS` / `DEFAULT_BACKGROUND_TIMEOUT_MS`，300s 是多条命令的统一撞墙点

### ③ 方案 C：批量编辑　→　**目标要重定义**
- 原目标「让 edit 并行」已证伪（收益 12 秒）
- 新目标：**「减少 round trip 数」**——每少一轮省 13.8s
- C1 措辞要从「并行」改成「一轮读全、改全、验完」
- 详见 `C-批量编辑.md`

### ④ 方案 A：耗时统计　→　**A1 已完成**
- 四个只读探针在 `.sicode/scratch/`，可重复跑
- A2（turn 粒度聚合）范围缩小：不用新埋点，现有字段够
- 详见 `A-耗时统计.md`
