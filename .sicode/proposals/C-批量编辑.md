# 方案 C：批量编辑（让模型一条消息发多个 edit）

> 状态：待评审　｜　**已用真实数据重估，优先级下降**（见下方「数据修正」）

## ⚠️ 数据修正（先读这段）

A 方案实测出来后（`.sicode/proposals/A-耗时统计.md`），这个方案的前提被推翻了一半：

| 实测 | 值 |
| --- | --- |
| `edit` 调用次数 | 385 次 |
| `edit` 总耗时 | **0.2 分钟**（约 12 秒） |
| `edit` 中位耗时 | 22ms，最慢 0.3s |
| 模型时间占漏斗 | **66.6%**（35897s / 53859s） |
| 平均每轮模型时间 | **13.8s** |

**把 edit 从 22ms 优化到 0（假装无限并行），也只省 12 秒 = 总墙钟的 0.02%。**

所以「并行改」这个动作本身几乎没有收益。真正值钱的是 **减少 round trip 数**：每少一轮 = 省 13.8s 的模型时间。

**目标重定义：不是「让 edit 并行」，而是「让模型一轮内把该改的都改完」。**

（当前并行度实测：一条消息 1 个工具 2281 次、2 个 283 次、3 个 23 次——87% 是单工具。）

## 问题

你的原话：「知道哪是改点，然后并行改」。

现实是模型**一个一个地改**：读一个文件、改一处、再读下一个、再改一处。历史统计：**79% 的轮次只发 1 个 tool call**（平均 1.1、最大 3）。

## 关键结论：引擎早就支持，缺的只是「模型的意愿」

我把端到端都核实了：

| 环节 | 状态 | 证据 |
| --- | --- | --- |
| 请求层 | ✅ 从不发 `disableParallelToolUse` | 全仓零命中 |
| 解析层 | ✅ 支持多 tool_call（含省略 index 的网关） | `openai-chat.ts:1103-1154`，我写临时测试验证过 |
| 执行层 | ✅ 每条 tool-call 到达即 `forkScoped` | `step.ts:121-133`，`:103` 注释确认无共享写队列 |
| 文件锁 | ✅ 不同文件真并行，同文件串行保序 | `edit.ts:320` 的 `withLock([path])` |

**所以这不是「造并行」，是「让模型用起来」。**

## 方案空间

### C1　强化提示词（已部分落地，可再加）

现在 `deepseek.txt` 已有 `# Batch independent edits`（你之前拍板的那版）。但它是**格言**，缺判据和边界。

从 DeepInfer 的 DSpark 借一个结构（投机解码 ↔ 批量编辑是同构的）：

| DSpark | 对应到编辑 |
| --- | --- |
| 置信度剪枝（低置信不进批） | **没定位的改点不进批**，先读 |
| 有界验证（按负载定长度） | **批后只验一次**，深度按风险 |
| 后缀衰减（越靠后越不可靠） | **批越长尾部越可能过时**，长批后重新落地 |

比 Cursor 的 `DEFAULT TO PARALLEL`（举证责任反转）温和，但给了**可操作的判据**——「证据是否已足够（改点是否已定位）」是模型自己可判的，不是态度问题。

### C2　计划-执行两段式

让模型先输出「改点清单」（哪些文件、哪些位置），用户或框架确认后，再一次性发全部 edit。

- 优点：不改引擎，纯提示词 + 可能的 UI。
- 缺点：多一次往返，除非清单能省下更多轮；且「确认」这一步对你是负担。

### C3　worktree 并行流

多个 agent 各在自己 worktree 改，最后合并。

- 这是 **Local fan-out**，不是并行工具调用——你明确说过「不是子代理」。而且合并冲突的成本可能高于收益。
- 本仓库已有 `packages/core/src/worktree.ts`，技术上可行。

### C4　快速 apply 管道

学 Cursor 的 apply model：主模型只出简化代码块，小模型负责落盘。

- 这是**产品级投入**（要训/选一个 apply 模型），不在提示词量级。作为长期方向，不是现在。

## 建议

**优先级：B（诊断回灌）> shell 超时治理 > C。**

理由（全部来自实测）：

- C 的收益上限是 12 秒（edit 总耗时），**天花板就在那**。
- B 省的是 13.8s/轮——一次「改错到下一轮才发现」的循环就是这个量级，量级高两个数量级。
- shell 有 241 分钟的池子（437 个 >5s 的调用，多半是超时等待），不碰 A/B/C 任何一个。

**C 仍然值得做，但目标改成「一轮改完」：**

- **C1 的措辞要重写**：现在的 `# Batch independent edits` 讲的是「一次发多个」，应该改成**「一次读全、一次改全、一次验完」**——重点是压缩轮次，不是提高并发。
- C2（计划-执行）反而更贴题意：先出改点清单再一次执行，直接减少轮次。
- C3/C4 维持搁置。
