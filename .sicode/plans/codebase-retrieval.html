SiCode 代码定位方案：全网调研结果

2026-10-29 · 起因：那个改设置页的会话，模型猜了 7 次关键词、走了 21 轮才找到根因
最重要的发现：Cursor 在 2026 年 7 月把自己的「向量索引」砍掉了。
它改用本地超快词法索引（Instant Grep）+ 子代理。也就是说——别再抄 Cursor 的向量索引了，它自己都不用了。网上大量讲 Cursor 向量索引的文章都是过时的。

二、向量检索到底有没有用？两边证据都摆出来

说没用的证据 多数派

· BM25（升级版关键词检索）在 SWE-bench 检索任务上打赢了 8 个向量模型里的 6 个
· 实测同样的准确率，向量方案贵 4 倍（返回的是代码片段，缺上下文，模型得反复补搜）
· SWE-bench 早期基线：纯向量 RAG 只有 1.96%，改用工具后 12.47%

说有用的证据 恰好是我们的场景

· 2026 年 8 月一篇严格实验：概念型问题（"哪些文件负责 XX"）上，向量检索 65.2% vs 硬搜 46.2%，高出 19 个百分点，还便宜 2.3 倍
· 我们的慢会话「侧栏底部留白」正是这种问题——中文意图对英文代码，关键词永远搜不到，这就是模型猜 7 次全落空的原因

结论

不是二选一，是分层用：找具体符号 → 词法秒杀；只能描述意图（尤其中文）→ 语义补位。两条腿都要，但分工明确。

三、补充调研：CodeGraph（结构层，值得和语义 MCP 一起验证）

CodeGraph（colbymchenry）无向量，与我们同路

本地 tree-sitter 建调用图存 SQLite，8 个工具：搜符号、查调用者/被调用者、改动影响面分析、一键打包上下文。19+ 语言，保存后 2 秒增量同步。安装器自动检测 opencode 并写配置——SiCode 今天就能试。

独立实测（不是厂商数字）

· 需要跨语言追调用链的问题：成本 −16%，工具调用 16.5 vs 25 次——有用但远没官方吹的 62%
· grep 五次就能到的问题：几乎无差别
· 代价：常驻后台进程；会话窗口多 ~80% 检索上下文
· 警示：另一图谱项目 Solograph 把内置图谱砍了——「四个月 agent 从没问过结构性问题」。agent 用不用它，永远是最大变数

我们的验证安排（更新）

CodeGraph 验证「结构层」，claude-context 验证「语义层」，都是一行 npx 装上。我们的 repo map 已是它的迷你版（tree-sitter 符号+依赖边），缺的只是调用边和 callers/impact 查询——如果验证有效，这是第 1 层的自然延伸。

四点五、排名：最快 ≠ 最好

🥇 单项「最快」：Cursor Instant Grep 但只是「搜得快」

正则搜索 13ms，单项速度无敌。但它只是把「关键词搜索」这一步做到极致——前提是你已经知道要搜什么词。我们的慢会话里模型的问题不是搜得慢，是不知道该搜什么词（猜了 7 次全错）。所以它对我们那个场景无解。

🥇 综合「最好」：Augment Context Engine 厂商自测 + 要花钱

SWE-bench Pro 51.80% 第一（和 Cursor、Claude Code 同模型对比，差距全在检索层）。语义依赖图 + 跨仓理解确实是当前最强定位能力。但：数字是厂商自测；按次收费（$0.03~0.06/查询）；代码要上云。

🥇 性价比「最实用」：分层叠加（我们方案）免费 + 本地

行业给不出单一赢家时，收敛的都是分层：确定性索引（快而准）+ 查询扩展（解决中文意图）+ 可选语义兜底。每一层独立复现的真实收益：+20% / 待测 / +41%——叠加才是对 21 轮慢会话的正解。

一句话排名：搜得最快 = Instant Grep；定位最准 = Augment（贵、上云）；最适合 SiCode = 分层方案——因为我们用户的核心痛点是中文意图定位，且要免费、本地，这两个约束直接淘汰了前两名的主打场景。

五、我建议 SiCode 这么做（三层）

1

升级关键词搜索（先做，改动小）

把 ripgrep 裸搜升级成「分字段加权」：代码内容、符号定义、文件路径、i18n 键、CSS 类名分开打分。tree-sitter 设施我们已有，直接复用。Cody 实证这类升级约 +20%。

2

教主模型「先翻译再搜」（零成本，这是关键层）

既然已经对接了 AI，最便宜的语义层就是主模型自己：在提示词里教它——搜不到时先把中文意图翻译成英文候选词（「侧栏底部留白」→ sidebar / footer / empty / flex），再搜同义词。零新模型、零索引。Cursor 弃向量正是同款逻辑：模型够聪明，缺的是指引。

3

向量检索交给生态，不内建 本地模型方案已砍

本地 embedding 模型没有意义——主模型本来就看得见代码，「隐私」不成立。想要向量检索的用户自己挂 MCP（claude-context 等），SiCode 提供配置示例即可，不背 400MB 下载和索引工程。

六、要达到 Cursor / Augment 的效果，分别要补什么

目标 A：追平现在的 Cursor（Instant Grep + Explore 子代理）

① Instant Grep 等价物 = trigram 倒排索引：SQLite FTS5 就能做（CodeGraph 实测 1105 文件 5 秒建完、2 秒增量），tree-sitter 分词 + FTS5 表 + 倒排查询。只对 1 万+ 文件的仓库有显著收益，本仓这种 250ms 的不急。
② Explore 子代理 = 隔离搜索上下文：opencode 本来就有 subagent 机制，配一个受限 agent 预设（只给 grep/read/glob 三件套 + 快模型），搜完只回传结论不回传正文。这是防「搜索垃圾撑爆主会话」的关键，而且成本很低。
③ 查询扩展指引（我们第 2 层）——Cursor 没有的，我们对中文用户反而更有优势。

工作量：① 一周内、② 两三天、③ 一天。合计约两周，全部本地免费。

目标 B：追平 Augment Context Engine（语义依赖图）

它的核心是三件套，逐个看我们怎么补：
① 调用图 + 影响面分析：repo map 已有符号和依赖边，缺的是「调用边」（tree-sitter 提取 call 表达式）和 callers/callees/impact 三个查询。这是 repo map 的自然延伸，一两周。
② 框架感知路由（React Router/Django 式的「URL→处理函数」跳转）： CodeGraph 支持 13 个框架，我们按用户量先做 React/Vue 两三个。
③ commit 历史索引（Context Lineage）+ 跨仓库：这个不追——工程量巨大、收益主要是企业级多仓场景，SiCode 用户单仓为主。

工作量：①+② 约 2~3 周。③ 明确放弃。诚实说：追平的是用户可感知的效果（改接口前知道影响面、跨文件追调用链不看运气），不是 feature 清单对齐。

路线图（按收益/成本排序）

第一阶段（✅ 已落地 2026-10-29）：查询扩展指引（OPENCODE_QEXPAND）+ BM25F 字段加权（OPENCODE_RANKED，grep 空结果自动注入建议）—— 预期解决慢会话的一半问题
第二阶段（下周）：Explore 式搜索子代理 —— 防上下文污染，所有用户受益
第三阶段（再做）：trigram 索引（大仓库）+ repo map 加调用边/impact —— 对齐 Cursor 与 Augment 的核心能力
持续旁路：CodeGraph MCP 挂着验证，如果第三方做得够好就不自研重复轮子

诚实的天花板：Augment 靠语义依赖图 + commit 历史拿了 SWE-bench Pro 第一，那是它全公司的核心业务；我们两周追的是它「用户可感知的 80%」（调用图、影响面、快搜索），剩下 20%（跨仓、历史谱系、语义图）明确放弃或交给 MCP 生态。免费 + 本地 + 中文扩展，是我们对它们没有的差异化，不是劣势补偿。
定稿结论（v6，覆盖本文早前的语义层讨论）：语义层 / 本地 embedding 模型最终不立项——标识符任务实测 −4pp，概念题 +41% 只来自论文而非本仓任务，还要为它背 25~400MB 下载与查询时的短促内存占用，与「不用本地模型、不常驻内存」冲突。方案收缩为纯词法 + 结构 + 搜索子代理三层，零模型、零下载、开箱即用。本文前述对向量/语义层的对比分析仅作为调研记录保留，不作实施方案。
