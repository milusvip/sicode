v4 修订（用户定调：面向用户的能力直接做好，不推第三方 MCP）：
① 检索能力一律原生内建：不推第三方 MCP——第三方工具描述是通用文案、不在我们的提示词体系里，adoption 差正是两份独立证据指出的死穴。原生工具才能：贴合场景的描述 + system.txt 指引 + grep 空结果自动注入建议。
② 语义层（本地 embedding）砍掉：本地模型是负收益——标识符任务实测 −4pp，概念题 +41% 只来自论文、非本仓任务；还要为它背 25~400MB 下载与查询时的短促内存占用，不值。embedding 与「不用本地模型、不常驻内存」的定调冲突，直接不立项。
③ CodeGraph 验证角色变更：从「给用户的替代品」降为「自研前的设计参考 + 基线对照」，仍然做，半天。
④ 结构层直接立项：与验证并行，验证结果修正设计。
要解决的问题：模型用中文描述意图时，在英文代码库里靠猜关键词定位，慢会话 21 轮、88% 步数花在探索。
验收指标（贯穿所有阶段）： ① 探索调用数 / edit 数的比值（现在基线 33:4 ≈ 8:1，目标 < 4:1）· ② 首 5 轮内命中目标文件的比例 · ③ 同类任务的总轮数

动作 0：CodeGraph 验证（第一个做，半天出结构层结论）

为什么排第一 收益证据最硬

  • 结构层是唯一有独立复现数据的方向：追调用链任务步数 −34%、成本 −16%（rustman 10-27 实测）
  • 装上就测：npx @colbymchenry/codegraph 自动识别 opencode；拿黄金问题集跑「改这个签名影响哪些文件」「这条调用链怎么走」两类任务
  • 两个产出：① 结构层（3a/3b）的基线对照数据 ② 它「哪里好用哪里不好用」的设计清单（直接修正 3a 设计，绕开它踩过的坑）

阶段一：查询扩展 + 关键词加权（两个都做，各管一半问题）

1a. 查询扩展指引 先做这个，一天

  • system.txt（packages/core/src/session/runner/prompt/system.txt）的搜索守则区加一条：搜不到目标时，先把用户意图展开成多组英文候选词（组件名、CSS 类、i18n 键、错误串），每组重试后再升级手段
  • grep/glob 工具描述内嵌一句：空结果 ≠ 不存在，先扩展同义词/拆词再重试，3 次仍空则换 glob 或读目录结构
  • 对照物：参考 shell.ts 里 detectPollingWait 的守则写法；开关 OPENCODE_QEXPAND=0 可关
  • token 预算（硬约束）：指引总量 ≤ 250 token/请求（参照 design-hint 压缩纪律：这是每步都付的税）。超出就砍，不挤占别的
  • 风险如实登记：收益 −30~50% 是预估、无文献数；本仓先例提示「写了指引模型未必照做」。所以 1a 上线即跑 A/B，数据不支持就撤，不恋战

1b. BM25F 分字段加权 恢复立项：与 1a 各管一半

  • 字段加权：文件路径 / 符号定义（tree-sitter 已有）/ 内容；i18n 键与值（zh 字典）进符号字段——中文 UI 文案直接可搜；CSS 类名（BEM 拆分）进符号字段
  • 与 1a 的分工：1a 解决「中文意图→英文代码」断链；1b 解决「半猜半搜的命中率」——两个失效模式不同，收益叠加而非二选一（Cody 实证约 +20%）
  • 落点：新模块 packages/core/src/search-ranked/，查询 → path + 得分 + 命中字段；在 grep 空结果时自动注入建议（不靠模型主动调用，绕开 adoption 风险）
  • trigram 倒排跟在 1b 后面做，同一模块（v6：本仓 8k 文件即有 50~70× 实测收益，见 3b）

阶段二：搜索子代理（下周，约 3 天）

Explore 式隔离搜索 对齐 Cursor Explore

  • 新增受限 agent 预设：工具只给 grep / glob / read（无 edit/write），模型用快档
  • 输出契约：只回传「结论 + 文件:行号清单」，不回传文件正文——防止搜索垃圾撑爆主会话
  • 主 agent 提示词加触发指引：「大范围定位类任务先派搜索子代理」
  • opencode 已有 subagent 机制（packages/core 内置），主要工作是预设配置 + 回传格式约束
  • 价值独立成立：即使阶段一失效，这一层也减少上下文污染

阶段三：结构自研（v4 直接立项，与验证并行，约 2 周）

3a. repo map 补调用边 + impact 查询 v4：直接立项

  • tree-sitter 提取 call 表达式 → 建调用边（repo map 现在只有 import 边）
  • 三个新查询暴露给工具层：callers（谁调用它）、callees（它调谁）、impact（改这个签名影响哪些文件）
  • 已知弱项照旧登记：go/rust/java 动态调用解析不准，标「近似」
  • 注意：调用边会增加索引构建时间（本仓冷启 5.8s → 预计 8~10s），增量缓存必须同步做，否则倒退

3b. trigram 倒排索引 v6 升级：本仓就有质变，不是大仓库专属

  • 第一手实测纠正（Cursor 逆向，同机同仓 8654 文件）：稀有符号 indexed ~14ms vs 全库内容搜索 ~1000ms = 50~70×；常见词 3~4×。Agent 每轮 5~10 次 grep 多为符号名 → 每轮省数秒。此前「1万+文件才显著」的判断作废（250ms 是 rg --files 的速度，不是内容搜索）
  • 索引成本实测：全量构建 ~7s / 8019 文件 / 产物 87MB（源码 97MB）；近邻 commit 加载 0.8s；防抖合并更新、commit 锚定、不做周期重扫
  • 设计照抄点：路径 .git/<app>/crepe 式<commit>/ 目录；未保存 buffer 由工具层并搜（unsaved editors），不进索引；返回 path+line+text；head_limit 无默认 + 2000 行 / 15k 字符硬帽
  • 超越点：Cursor 候选集无相关性排序（doc_id 序），我们的 BM25F 排序是直接增益
  • 存储：SQLite FTS5（Cursor 是 Rust 原生二进制，我们用 FTS5 换实现简单；性能差距用实测验收）

第一手逆向校准（cursor逆向专区文档，2026-10-24 实测）

  • 来源：D:\软件丨工具\cursor逆向专区\文档\ —— Cursor-本地Trigram索引存储结构 / Cursor-本地检索与索引全链路（对真实仓库 + crepectl 实测，非博客二手信息）
  • 抄能力最小清单（逆向文档原文）：① commit 级文件倒排（可选，加速用）② 工具执行时 ripgrep 并搜 unsaved editors（必须，「刚写的就能搜到」）③ 返回 path+line+text（必须）④ 不要为 grep 实现 Merkle/向量合并（不要）
  • adoption 手法（Cursor 亲测）：Cursor 把语义与正则分成不同工具、不自动混排；我们无语义层，对应的做法是 grep/glob/read 三层工具分工明确、output_mode 默认 content 但用工具描述教模型自选——照此设计
  • 三条管道别揉一起（逆向图）：本地文本倒排（Crepe）/ Merkle 云端增量 / 语义向量检索是三条独立管道——我们只做前两类（trigram 倒排、repo map 调用边），语义向量检索明确不做，其余不合并

内部验证：CodeGraph 作为设计参考（不面向用户）

  • 本机装 CodeGraph（npx @colbymchenry/codegraph）——v4 角色变更：不是给用户的替代品，是我们自研前的设计参考
  • 拿黄金问题集跑它的 callers/impact/context，产出两份东西：① 我们结构层的基线对照数据 ② 它「哪里好用哪里不好用」的清单（直接修正 3a 设计）

验证方法（每阶段同一把尺，v2 加强）

  • 黄金问题集：从真实会话收 20~30 条「中文意图定位」问题（设置页留白、token 字样、反代卡住…），每条人工标注目标文件:行号
  • 二值评分：前 5 轮是否命中目标文件（recall@5）；总轮数、工具调用数作辅助指标
  • 指标按任务类型分层（v2）：探索/edit 比在「提问型」和「改码型」任务上基线不同，混在一起比会失真——分两层各记各的
  • A/B 配对跑（v2）：开关切换新旧行为，同一问题新旧各跑、每条至少 3 次取多数（免费模型波动大，2 次会翻转）；报告区间而不是单点数
  • 指标进 notes.md 对应区域，按阶段更新

落地注意（v2 新增）

  • 增量策略统一（v6 明确）：不做后台 watcher 守护进程（CodeGraph 那种，资源代价不值）。1a 零索引；1b/3a 沿用 repo map 现有 mtime+size 懒失效（冷启 5.8s/热 0.39s，已验证）；trigram 用 commit 锚定式——索引锚 git commit、未提交改动叠加其上、仅大漂移时重建（Cursor 官方机制），非 git 仓库查询时按 mtime 懒检查。本仓全量重建也才 ~7s（逆向实测同量级），增量压力天然小
  • 与现有 hint 机制的关系：查询扩展指引走 system.txt 静态区 + 工具描述，不新增 hint 注入点——context.ts 已有 context-hints/clarify-hint/design-hint 三个，不再挤
  • 并行会话冲突：prompt 文件正被其他会话改，落地前先 git status 确认，改完立即提交不留在工作区
  • 回滚开关：1a 用 OPENCODE_QEXPAND=0；阶段二子代理用 agent 配置开关；每个能力独立可关

兼容性：开箱即用与全模型适配（硬约束）

  • 开箱即用：全部动作（指引/加权/结构/子代理）100% 开箱，零下载、零用户动作、零模型——纯词法 + 结构 + 隔离搜索，全程免费本地。
  • 与对话模型解耦：没有任何本地模型，检索不碰 embedding，与用户用什么对话模型（DeepSeek 免费档/Kimi/任何）完全无关。
  • 不依赖模型自觉的两条保险：BM25F 建议由代码逻辑触发（grep 空结果 → 自动注入），结构建议同理——弱模型不照做指引也躲不过；强模型额外受益于提示词指引
  • 工具协议零特殊处理：新工具走 opencode 现有 OpenAI-compatible tool calling 通道，DeepSeek function calling 标准支持
  • 预期差如实登记：同一指引强模型照做度高、免费档低——A/B 按模型分档测，「自动注入」比「提示词恳求」重要
一句话方案：三层原生全做——词法（查询扩展 + BM25F）、结构（调用边/impact，CodeGraph 只当内部参考）、隔离搜索子代理；每层独立可验收、独立可回滚，零模型、零下载、开箱即用。
