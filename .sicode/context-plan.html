P0 压缩后的历史回溯 已完成 · 真机通过

新增 tool/plugin/history.ts：读 SessionStore.messages() 全量， 以最后一条 completed 的 compaction 划界，之前的消息转文本后按关键词命中，无 query 则返回最近几段； 单段超 1500 字符保头 + 尾。注册在 plugin/internal.ts 三处（插件表 + SessionStore.Service + .node）。

真机实测：埋三个标记 → /compact → 要求必须查压缩前记录。模型主动调用 history，返回 2 of 2 archived exchanges, from before the last compaction metadata = { matches: 2, archived: 2, compactions: 1, truncated: false } 三个标记全部命中，未凭摘要作答。

P2 precompute 量化 埋点已完成 · 开关仍关

默认值没有改。原因不是缺骨架 —— Precomputed 的三态编排早就在， 缺的是数字：后台摘要即使没被用上也会扣费，而记账只在成功换入时发生， 原本连「白算了多少」都看不见。

现在补了两层。新增 compaction-metrics.ts 监听 Compaction.Started → Ended 配对算出压缩真正阻塞了多久（Ended 的 schema 里没有 duration，配对是不改内核的唯一算法）； session/compaction.ts 在 precompute 的三条路径各写一条 started（带窗口占比）/ used（带 savedMs 与 leadMs）/ discarded（带原因：overflow、stale-tail、superseded…）。

跑 bun script/compaction-stats.ts 出报告：p50 / p90 等待、used 与 discarded 的拆分、浪费率， 末尾直接给判据 —— 浪费 > 50% 保持关，25–50% 记作 marginal，< 25% 且累计省下 ≥ 30s 才判值得开。

E1 shell 输出中文乱码 已完成 · 字节验证

原规划里没有这项，是落地过程中撞见的：报错回传的中文全是 �。 根因是本机宿主 [Console]::OutputEncoding 为 gb2312 / codepage 936， 而 output() 一律 toString("utf8") —— 每个中文字符都变成替换字符， 恰好是解释命令为什么失败的那一行。

两层修：根因层在 PowerShell 参数前钉 [Console]::OutputEncoding = UTF8（带 try/catch， 无控制台宿主下不能连带整个命令失败）；兜底层新增 util/src/decode.ts 的 Decode.outputText()，严格 UTF-8 优先，win32 才退 GBK。

真实 CP936 字节，同一个输入： 修复前 toString("utf8") → "�޷��� Null �������������" 修复后 Decode.outputText → "无法对 Null 数组进行索引。" 修前那串和真机会话里看到的逐字符一致，修后完整还原。
关键细节：判断编码前要先剔掉尾部不完整的多字节序列。否则分片读取把字符切成两半时， 合法 UTF-8 会被判成「不是 UTF-8」而整段走 GBK —— 修一个乱码，造出另一个。

E2 trigram 索引复用判据 已完成 · 修掉静默错答

也是规划外发现的，起因只是回答「索引对比为啥不做」。索引的存储结构没问题， 但「下次启动还能不能复用这份索引」的判据只比路径集合，于是有两个洞，而且互相掩盖：

洞一：复用从来没生效过。二进制文件被 replaceAll 跳过、不写行， 而 current 来自 rg --files 会把它们列出来 ⇒ 两边集合大小永远不相等 ⇒ 每次启动都在后台做一次全量重建。本仓有 269 个 .png，足以触发， 所以那「10 秒一次性」其实每次都付，只是看不见。

洞二：路径不变、内容变了，就复用旧 trigram。（SiCode 关闭期间的外部编辑，或只改内容不加文件的 git pull）预筛会把这个文件从候选里丢掉，grep 报 0 条命中 —— 这是错误答案，不是慢。洞一正好把它藏住了：既然从不复用，也就从不读到过期的 trigram。

服务层探针（真实工具链，不是模拟）： 文件里确有 tokenZZZ → {"matches":0,"prefiltered":true} · "No matches found" 修后同一条用例 → matches:1，且旧 token 正确变成 0 两条新测试都做了基线：旧代码上都会失败，才算真的抓住。
不能靠「候选为空就退回全量 rg」兜底：那会把每次未命中的成本从 0 变成 3.5–4.4 秒全扫， 把预筛的收益整个打掉。只能修索引本身的时效性。

明确不做的三项含理由

不做 语义索引 / embedding

Cursor 的语义检索在云端，本地同样只有 trigram 倒排。SiCode 是本地优先、用户自带 key， 没有云端 embedding 管道可挂；要做得引入「用户自配 embedding provider」，成本和不确定性都高。 想提升「相关文件进上下文」，P0 的历史回溯 + 现有 FTS5 的 bm25 排序，性价比明显更高。 落地 P0 之后这条更站得住：原文已经能被检索回来，缺口不在「语义」这一层。

不是缺口 检索结果自动注入

Cursor 逆向明确写了「不把整库检索结果当隐式上下文自动塞进 prompt」，靠工具描述教模型自己选。 SiCode 的 project-map 反而每次请求都注入 repo map 和 notes 标题索引 —— 这一项 SiCode 走在前面，不需要对齐，要考虑的是注入体积是否该收。

不做 重做索引层（速度）

上面对照用的样本就是本仓：查询加速同为 40–80× 一档，建索引慢 3 秒（一次性）， 但盘上占用 15MB vs 87MB，只有 Cursor 的 1/6。速度维度没有落后，重写是纯浪费。

但「不重写」不等于「不动」。复用判据那两个洞（任务卡 E2）是在索引层就地修的， 没有换存储格式，也没有引入新依赖 —— 该抄 Cursor 的是它按 commit 分目录的失效策略， 不是它那 6.85 秒。
